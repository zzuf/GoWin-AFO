# Existing Projects Audit

This document records an audit, centered on primary sources, of existing implementations referenced in this project's design and implementation. The initial research date was **2026-08-23**. Updates to adopted dependencies and official inputs were added on 2026-09-23. Unless stated otherwise, update status for comparison projects reflects the initial research date. Unless otherwise noted, counts are published by each project's own README; this project has not recounted or guaranteed them.

## Adopted Updates on 2026-09-23

- Pinned `microsoft/go-winmd` to [`16e7d31aeb8a`](https://github.com/microsoft/go-winmd/commit/16e7d31aeb8af4dd324c5c452e2263aa50b0f257). This uses generic/SZARRAY/signature improvements since the old `d6ac2179ffeb` pin and handles API renames in the adapter. It requires at least Go 1.26. Becoming parseable is distinct from proving a callable ABI.
- Updated Win32 metadata to [71.0.26-preview](https://www.nuget.org/packages/Microsoft.Windows.SDK.Win32Metadata/71.0.26-preview) and the Windows App SDK meta-package to [2.5.1](https://www.nuget.org/packages/Microsoft.WindowsAppSDK/2.5.1). The packages were retrieved and their hashes and dependencies checked; license/NOTICE files were byte-identical to the old pins.
- Kept WDK metadata at `0.13.25-experimental`. The ABI oracle still uses installed SDK `10.0.26100.0`. Pinned the retrieval source for WinRT input to the official `Microsoft.Windows.SDK.CPP/10.0.26100.7705`, which contains identical bytes ([CI fix record](updates/2026-09-23-ci.md)). Even if a newer SDK exists, do not automatically switch to unverified headers/contracts.

Here, "reuse" means taking code or a library as a dependency. A "comparison oracle" is an implementation against which names, signatures, layouts, diagnostics, and runtime results derived from the same official inputs are compared; it does not mean copying its generated output as a primary source. Microsoft's WinMD, Windows SDK/WDK, and Windows App SDK are primary inputs. Generated bindings from `windows-rs`, CsWin32, and Deployment Theory are not primary inputs. See [licensing.md](licensing.md) for licensing and redistribution policy.

None of the audited projects directly meets this task's combined requirements: stable IDs for every ingested symbol, complete backend/status classification, `unclassified = 0`, independent C/C++ ABI oracles for x86/x64/ARM64, and unified coverage across Win32/WDK/WinRT/App SDK/headers/TLBs. Accordingly, this project retains ownership of official inputs, normalized IR, classification, coverage, and ABI verification while using existing comprehensive projection rules and tests for comparison.

## Audit Method and Scope of Assurance

- Licenses are distinguished between each repository's LICENSE and, for Microsoft, separate licenses bundled with artifacts. An MIT GitHub repository does not necessarily make its SDK/WDK/NuGet payload MIT-licensed.
- Update status was checked against GitHub commits/releases. Where there was no release, it is recorded as "none" without inventing a version number.
- ABI verification distinguishes (1) consistency among metadata, (2) compilation of generated code, (3) Windows runtime tests, and (4) independent `sizeof`/`alignof`/`offsetof`/signature oracles using MSVC/Clang and SDK headers. The first three alone are not treated as equivalent to (4).
- "Known skips" include only items confirmed in public settings, diagnostics baselines, code, or documentation. Where no exhaustive skip list is public, the status is "unknown."
- Because GitHub default branches can change, update status includes immutable commit links. Design links point to default branches for readability.

## Microsoft Projects

### `microsoft/go-winmd`

- **License and update status:** [MIT](https://github.com/microsoft/go-winmd/blob/main/LICENSE). HEAD at research time was [`d6ac2179ffeb2d1dae3fcea365f9ea24d92ae1f1`](https://github.com/microsoft/go-winmd/commit/d6ac2179ffeb2d1dae3fcea365f9ea24d92ae1f1), 2026-08-22. No GitHub Release could be confirmed.
- **Input and API surface:** A Go library for reading ECMA-335 metadata streams/tables, blobs/signatures, and custom attributes in PE/CLI files. The [`winmd` package](https://github.com/microsoft/go-winmd/tree/main/winmd) is a largely language-neutral WinMD reader, not a finished generator for specific Win32/WinRT API surfaces. The repository's [`cmd/gowinmd`](https://github.com/microsoft/go-winmd/tree/main/cmd/gowinmd) is an experimental front end for Go output.
- **Architecture and organization:** The parser is independent of host and target. `gowinmd` golden output covers 386, amd64, and arm64, but this does not guarantee the entire Windows ABI surface. The reader, table rows/models, and signature/custom-attribute decoders are separated from the CLI and golden output.
- **Types, functions, COM, and WinRT:** It reads foundational projection data including TypeRef/TypeDef, Field, MethodDef, MemberRef, Constant, CustomAttribute, ImplMap, generics/signatures, and architecture attributes. P/Invoke functions can be extracted. COM and WinRT can be read as metadata, but complete COM vtable/runtime and WinRT activation/generic IID projection are not provided.
- **ABI verification:** It has ECMA-335 parser tests and generated golden output, but no independent `sizeof`/`offsetof`/calling-convention oracle that measures SDK headers with MSVC/Clang. [CI](https://github.com/microsoft/go-winmd/blob/main/.github/workflows/test.yml) also focuses on parser/generator tests.
- **Generated output:** `gowinmd` emits Go types and `mkwinsyscall` declarations from selected namespaces and functions. It is not a complete checked-in binding tree for every namespace.
- **Known skips/limitations:** On wildcard selection, the current `gowinmd` does not emit methods without ImplMap as P/Invoke functions, and its representation of nested types is not the same as this task's provenance/ABI IR. No public guarantee says it fully handles varargs, packed/bit-field types, special calling conventions, or COM/WinRT runtimes. Do not equate information retained by the parser with information projected by the emitter.
- **Tests:** Unit tests cover tables/indexes/blobs/signatures/custom attributes and malformed inputs; there are Windows metadata fixtures and golden output for 386/amd64/arm64. The public test tree does not establish whether fuzzing or full-SDK ABI probes exist.
- **Adoption decision:** **Directly reuse the ECMA-335 reader** pinned in `go.mod`. Avoid duplicating a parser unnecessarily; add missing rows/attributes/diagnostics with minimal reproduction fixtures and changes suitable for upstreaming. The `gowinmd` emitter does not meet this task's stable-ID, complete-classification, or backend-matrix requirements, so use it for comparison rather than adopting it unchanged.

### `microsoft/win32metadata`

- **License and update status:** Repository code is [MIT](https://github.com/microsoft/win32metadata/blob/main/LICENSE), but that LICENSE explicitly does not change the license of input headers. HEAD at research time was [`d0f363037c6987790b3548b7f82f382034d86bf2`](https://github.com/microsoft/win32metadata/commit/d0f363037c6987790b3548b7f82f382034d86bf2), 2026-08-18. The latest public release was [`v71.0.20-preview`](https://github.com/microsoft/win32metadata/releases/tag/v71.0.20-preview), 2026-08-19. `sources.lock.json` is authoritative for this project's actual pin; it is not automatically set to the latest version at research time.
- **Input and API surface:** This official Microsoft project parses Windows SDK headers and supporting settings to create `Windows.Win32.winmd` in the `Microsoft.Windows.SDK.Win32Metadata` NuGet package. [Architecture](https://github.com/microsoft/win32metadata/blob/main/docs/architecture.md) describes scraping, metadata transforms, and WinMD generation; [projection guidance](https://github.com/microsoft/win32metadata/blob/main/docs/projections.md) describes consumer interpretation. It covers Win32 functions, DLLs/entry points, structs/unions/enums/constants/typedefs/handles/callbacks, GUIDs, COM interfaces, and custom attributes. It is not a substitute for WinRT contract metadata.
- **Architecture and organization:** Differences among x86, x64, and ARM64 are retained in `SupportedArchitecture` and architecture-specific definitions. Consumers filter for the target architecture instead of incorrectly collapsing them into one common definition. The generated NuGet package's main artifact is one namespaced WinMD; it does not prescribe a Go/C#/Rust binding layout.
- **Types, functions, COM, and WinRT:** It includes attributes representing native widths, pointers, arrays, P/Invoke, SetLastError, NativeArrayInfo, MemorySize, NativeTypedef, FreeWith, RetVal, associated enums, and deprecation/availability equivalents. It represents COM interface inheritance and method order. WinRT runtime classes/activation are outside its scope.
- **ABI verification:** [`IntegrityTests.cs`](https://github.com/microsoft/win32metadata/blob/main/tests/Windows.Win32.Tests/IntegrityTests.cs) checks metadata integrity, duplicate/missing references, attributes, etc.; [`InterfaceTests.cs`](https://github.com/microsoft/win32metadata/blob/main/tests/Windows.Win32.Tests/InterfaceTests.cs) checks COM/interface information. There are also regression checks using baselines/PDB/JSON. The repository tests do not establish an independent, machine-readable `sizeof`/`alignof`/`offsetof` oracle comparing every public type with MSVC/Clang SDK headers for each target.
- **Generated output:** The official artifacts are the WinMD and related metadata/config in NuGet. Consumers generate language bindings.
- **Known skips/limitations:** [`scraper.settings.rsp`](https://github.com/microsoft/win32metadata/blob/main/generation/WinSDK/scraper.settings.rsp) contains header/symbol/macro include, exclude, and allow lists plus manual corrections. C preprocessor macros, inline constructs, bit-fields, compiler intrinsics, and unparseable signatures may not be representable or included in WinMD alone. This project must inventory header symbols absent from official metadata through a header provider, rather than inheriting exclusion reasons as its own statuses.
- **Tests:** .NET unit/integrity tests, interface/method-order tests, and generated-baseline diff detection. Generated Go ABI/runtime tests are outside this repository's responsibility.
- **Adoption decision:** Read the pinned, hash-verified NuGet WinMD as the **official primary Win32 source**. Use the metadata repository's settings and tests as evidence for provenance and difference investigations. Classify header-only symbols absent from the official WinMD through the Clang provider or as `missing-upstream-metadata`, rather than treating them as nonexistent.

### `microsoft/wdkmetadata`

- **License and update status:** Repository code is [MIT](https://github.com/microsoft/wdkmetadata/blob/main/LICENSE), but WDK/SDK inputs have separate terms. HEAD at research time was [`fbb3a13785073a707c6171bffbd5522438031732`](https://github.com/microsoft/wdkmetadata/commit/fbb3a13785073a707c6171bffbd5522438031732), 2026-08-05. The latest public release was [`v0.13.25`](https://github.com/microsoft/wdkmetadata/releases/tag/v0.13.25), 2024-11-13. The actual pin, including NuGet's experimental suffix, is fixed in `sources.lock.json`.
- **Input and API surface:** This official project generates `Microsoft.Windows.WDK.Win32Metadata` from WDK headers and Win32 metadata/tooling. [Build orchestration](https://github.com/microsoft/wdkmetadata/blob/main/BuildTools/BuildTools.proj) and [`Windows.Wdk.proj`](https://github.com/microsoft/wdkmetadata/blob/main/generation/WDK/Windows.Wdk.proj) show source/build dependencies. It may include WDK native types, enums, constants, callbacks, functions, and COM-style interfaces, but it is not a WinRT provider.
- **Architecture and organization:** WinMD includes definitions according to WDK profile and target architecture. It also contains type references shared with the SDK, so consumers must deduplicate without losing assembly/source provenance. It does not generate language-specific package trees.
- **Types, functions, COM, and WinRT:** It provides types, constants, and function metadata across kernel and user mode. Presence in metadata does not imply that a normal Go user process can call a DLL export or that a Go driver can be built. Treat COM-like interfaces as native interfaces, distinct from WinRT projection.
- **ABI verification:** [`IntegrityTests.cs`](https://github.com/microsoft/wdkmetadata/blob/main/tests/Windows.Wdk.Tests/IntegrityTests.cs) checks metadata integrity and baselines. An independent MSVC/Clang `sizeof`/`offsetof` oracle for all types and architectures, and user/kernel execution classification, could not be confirmed.
- **Generated output:** The WDK WinMD in NuGet is the main artifact. The Go binding layout/backend is the consumer's responsibility.
- **Known skips/limitations:** Mechanical counting of [`scraper.settings.rsp`](https://github.com/microsoft/wdkmetadata/blob/main/generation/WDK/scraper.settings.rsp) found 784 `--exclude` entries and 2,034 `--remap` entries at research time. These are scraper-settings counts, including duplicate replacements and manual supplementation, not a total of skipped final symbols. Reasons and granularity differ by item. Header-only, compiler-specific, kernel-only, and incomplete-metadata cases need separate classification rather than one skip category. Also, do not treat the old README's SDK/WDK Build 22000 description as the current tool pin; prioritize the `10.0.22621.755` in [`BuildTools.proj`](https://github.com/microsoft/wdkmetadata/blob/main/BuildTools/BuildTools.proj) at research time and the actual package manifest for each version.
- **Tests:** Build/integrity/baseline tests. No runtime suite could be confirmed that classifies every safe call from a normal user process, UMDF, kernel-only case, and type-only case.
- **Adoption decision:** Ingest as a separate source ID and the **official primary WDK source**. Normalize without simply generating SDK types with the same names twice, and preserve provenance. Use DLL exports, documented execution environments, and header evidence to classify `user-mode`, `UMDF`, `type-only`, `kernel-mode-only`, and `metadata incomplete` independently in this project.

### `microsoft/windows-rs`

- **License and update status:** [MIT](https://github.com/microsoft/windows-rs/blob/master/license-mit) OR [Apache-2.0](https://github.com/microsoft/windows-rs/blob/master/license-apache-2.0). HEAD at research time was [`acaaa37be53e68f8c1be575d24dcbebce1e92b1a`](https://github.com/microsoft/windows-rs/commit/acaaa37be53e68f8c1be575d24dcbebce1e92b1a), 2026-08-18. The latest public release was [`73`](https://github.com/microsoft/windows-rs/releases/tag/73), 2026-02-17.
- **Input and API surface:** [`windows-bindgen`](https://github.com/microsoft/windows-rs/blob/master/docs/crates/windows-bindgen.md) projects Windows metadata into Rust. It covers Win32, COM, and WinRT broadly, with separate runtime/core/support crates. The [dependency overview](https://github.com/microsoft/windows-rs/blob/master/docs/dependencies.md) shows crate relationships.
- **Architecture and organization:** It is divided into `windows` (idiomatic projection), `windows-sys` (low-level), `windows-core`, `windows-future`, `windows-collections`, etc. Namespace features avoid compiling unneeded surfaces. It covers multiple Rust-supported Windows targets, but does not prove Go's 386/amd64/arm64 backends correct.
- **Types, functions, COM, and WinRT:** It implements native types/functions/constants/callbacks, COM interfaces/vtables/QueryInterface, WinRT runtime classes/activation, HSTRING, delegates/events, async, collections, and generic/parameterized interfaces. It is among the most comprehensive Win32 and WinRT comparison targets.
- **ABI verification:** [`windows-clang`](https://github.com/microsoft/windows-rs/blob/master/docs/crates/windows-clang.md) and bindgen tests include header/Clang comparisons, RDL/golden output, C++/WinRT interop, and target-specific compile/runtime tests. The [test workflow](https://github.com/microsoft/windows-rs/blob/master/.github/workflows/test.yml) and [generation workflow](https://github.com/microsoft/windows-rs/blob/master/.github/workflows/gen.yml) check regeneration drift. However, a public, machine-readable `sizeof`/`alignof`/`offsetof` coverage report for every symbol × every architecture, as required by this task, could not be confirmed.
- **Generated output:** Crates and features are split by namespace/dependency, separating low-level `windows-sys` from ergonomic `windows`. This is a strong design reference for avoiding one huge package.
- **Known skips/limitations:** Bindgen generates reachable types from selected metadata/header surfaces. It does not unconditionally expose items outside header allowlists, functions without library mappings, unrepresentable rich variadics, special calling conventions (for example, some `__fastcall` cases), or complex C/C++ ABIs. No single public ledger of exact skip counts and all reasons could be confirmed.
- **Tests:** Code-generation golden/RDL tests, Clang/header comparisons, crate compilation, Win32/COM/WinRT runtime/interop, and multiple-target workflows. These are strong comparison evidence, but Rust ABI success must not be extrapolated to Go FFI success.
- **Adoption decision:** Use as a **comparison oracle** for COM/WinRT projection, parameterized IIDs, namespace-feature partitioning, low-level/ergonomic separation, and generation-drift tests. Do not copy generated Rust or reparse it as authoritative metadata. Implement Go runtime/FFI capability decisions and ABI oracles independently.

### `microsoft/CsWin32`

- **License and update status:** [MIT](https://github.com/microsoft/CsWin32/blob/main/LICENSE). HEAD at research time was [`b0f1e799e6aa793eccffafa6ba8164ca45a9266f`](https://github.com/microsoft/CsWin32/commit/b0f1e799e6aa793eccffafa6ba8164ca45a9266f), 2026-08-14. The latest NuGet package at research time was [`Microsoft.Windows.CsWin32 0.3.321`](https://www.nuget.org/packages/Microsoft.Windows.CsWin32/0.3.321), 2026-08-17. The GitHub release URL that NuGet gave for that version returned 404 at research time; the last GitHub Release whose contents could be confirmed was [`v0.3.298`](https://github.com/microsoft/CsWin32/releases/tag/v0.3.298), 2026-06-22. Do not conflate these three. The versioned NuGet page for 0.3.321 lists Win32Metadata `>= 71.0.14-preview`, WDK metadata `>= 0.13.25-experimental`, and Win32Docs `>= 0.1.42-alpha` as dependency inputs.
- **Input and API surface:** A C# incremental source generator using `Microsoft.Windows.SDK.Win32Metadata` or [compatible third-party metadata](https://microsoft.github.io/CsWin32/docs/3rdPartyMetadata.html). The [Generator](https://github.com/microsoft/CsWin32/blob/main/src/Microsoft.Windows.CsWin32/Generator.cs) emits requested APIs and dependent types. [`Directory.Packages.props`](https://github.com/microsoft/CsWin32/blob/main/Directory.Packages.props) at the researched HEAD pins Win32Metadata `71.0.14-preview`, WDK metadata `0.13.25-experimental`, and Win32Docs `0.1.42-alpha`. It covers Win32 P/Invoke, types, constants, COM, some metadata-represented macros, and friendly overloads, but is not a Windows SDK contract WinRT projection.
- **Architecture and organization:** The NuGet source generator and analyzer run in the consumer build, generating partial classes/types from selections in `NativeMethods.txt`. Architecture-specific APIs are filtered or diagnosed depending on target and request method. According to [architecture-specific API guidance](https://microsoft.github.io/CsWin32/docs/ArchSpecificAPIs.html), mismatched explicit requests produce `PInvoke005`, while mismatched wildcard requests are omitted.
- **Types, functions, COM, and WinRT:** It generates C# P/Invoke, structs/unions/enums/handles, delegates, COM interfaces, friendly overloads, SafeHandle, etc. It is not a comprehensive generator for WinRT runtime classes, activation, or parameterized IIDs.
- **ABI verification:** It has generator unit/golden tests, AnyCPU/x86/x64/arm64 Roslyn compilation through [`FullGenerationTests.cs`](https://github.com/microsoft/CsWin32/blob/main/test/Microsoft.Windows.CsWin32.Tests/FullGenerationTests.cs), and Windows runtime/COM tests. The native C/C++ fixtures in integration tests are limited; no independent, machine-readable ABI oracle could be confirmed that measures every generated type/signature against MSVC/Clang SDK headers per target. Do not treat .NET marshaler/source-generator success as evidence for the Go syscall ABI.
- **Generated output:** Requested APIs and transitive dependencies are generated by the consumer compilation's source generator/AddSource or build task. Multiple-file mode produces per-type `{Type}.g.cs`, `Delegates.g.cs`, P/Invoke partial classes, etc.; `emitSingleFile=true` produces `NativeMethods.g.cs`. Thus it does not emit the entire SDK as checked-in namespace packages. Friendly overloads and raw extern declarations are layered within the same generation ecosystem.
- **Known skips/limitations:** [`Generator.Invariants.cs`](https://github.com/microsoft/CsWin32/blob/main/src/Microsoft.Windows.CsWin32/Generator.Invariants.cs) records symbols not generated always or in marshaling mode, with alternative reasons. Examples include `GetLastError`, legacy/overridden integer and layout types, vectored-exception helpers, and `IUnknown`/`IDispatch`/`VARIANT` in marshaling mode. Architecture mismatches, macros/inline/header symbols absent from metadata, constructs that cannot be safely projected in C#/.NET, and APIs not reachable from a request also are not generated. Wildcard skips behave differently from diagnostics for explicit requests, so they cannot be reused unchanged as this project's complete inventory/status. The default `WideCharOnly=true` in [`GeneratorOptions.cs`](https://github.com/microsoft/CsWin32/blob/main/src/Microsoft.Windows.CsWin32/GeneratorOptions.cs) omits ANSI variants and removes W suffixes, differing from this project's policy of preserving both A/W forms under native names. No complete machine-readable ledger of known skips could be confirmed.
- **Tests:** Source-generator unit/golden tests; AnyCPU/x86/x64/arm64 compilation; diagnostics; bit-field/flexible-array/callback tests; and Windows COM/Direct2D/WMI/Shell runtime tests including [`ComRuntimeTests.cs`](https://github.com/microsoft/CsWin32/blob/main/test/GenerationSandbox.Tests/ComRuntimeTests.cs). The [build workflow](https://github.com/microsoft/CsWin32/blob/main/.github/workflows/build.yml) organizes them. The public suite is useful for C# projection quality, but WDK kernel classification, general WinRT projection, and Go callbacks/FFI are outside its scope.
- **Adoption decision:** Use as a comparison oracle for metadata-attribute interpretation, architecture diagnostics, friendly overloads, SafeHandle, and COM tests. Do not use generated C# as a primary input or port C# marshaling assumptions. This project independently owns raw/ergonomic separation, Go ABI backends, and header/WDK/WinRT classification.

## Deployment Theory Projects

### `deploymenttheory/go-winmd`

- **License and update status:** [MIT](https://github.com/deploymenttheory/go-winmd/blob/main/LICENSE). HEAD at research time was [`c9712c91de8ba2b634eac01edd2a280db234968e`](https://github.com/deploymenttheory/go-winmd/commit/c9712c91de8ba2b634eac01edd2a280db234968e), 2026-08-18. The latest public release was [`v1.0.0`](https://github.com/deploymenttheory/go-winmd/releases/tag/v1.0.0), 2026-08-14.
- **Input and API surface:** According to its [README](https://github.com/deploymenttheory/go-winmd), this ECMA-335 reader uses only the standard library to read PE/CLI, `#~`/`#-`, String/Blob/GUID heaps, sizing for 45 tables and the main 22 tables, signatures/generics, and constants/custom attributes. It is not itself a Win32/WinRT binding generator.
- **Architecture and organization:** It separates `pkg/winmd`, NuGet source helpers, an update command, and pinned test data. The parser is target-independent. Tests pin hashes/versions of real WinMDs.
- **Types, functions, COM, and WinRT:** It materializes TypeRef/TypeDef, Field/MethodDef/MemberRef, signatures, generics/custom attributes, etc., so it can read raw metadata across API surfaces, but provides neither a COM vtable/runtime nor WinRT activation projection.
- **ABI verification:** It has reader-correctness and real-WinMD traversal tests, but no oracle for generated language types or the C ABI.
- **Generated output:** It does not generate binding code. Update/fetch tools and fixtures are the main artifacts.
- **Known skips/limitations:** The README's non-goals include lazy row access, a general API for arbitrary coded-index tags, `#US`, and complete BYREF/multidimensional-array decoding. The README's comparison with other parsers reflects its writing date and does not establish the current state of the updated `microsoft/go-winmd`, so it is not a basis for adoption decisions.
- **Tests:** Truncated/malformed bounds, tables/signatures/custom attributes, and large-scale traversal of pinned `Windows.Win32.winmd` and `UniversalApiContract` fixtures. Published traversal counts are the project's own reports.
- **Adoption decision:** It is useful as a **differential oracle** for hostile-input handling, real-fixture regression, and parser fuzz corpora. This project already pins `microsoft/go-winmd`, however, and will not put two readers on the production path. Add reproduction tests for needed improvements and make changes suitable for upstreaming where possible.

### `deploymenttheory/go-bindings-win32`

- **License and update status:** [MIT](https://github.com/deploymenttheory/go-bindings-win32/blob/main/LICENSE). HEAD at research time was [`5421f07c62f07e5ebfc2c009c12de9bf0ead2c5f`](https://github.com/deploymenttheory/go-bindings-win32/commit/5421f07c62f07e5ebfc2c009c12de9bf0ead2c5f), 2026-08-21. The latest public release was [`v0.3.1`](https://github.com/deploymenttheory/go-bindings-win32/releases/tag/v0.3.1), 2026-08-14.
- **Input and API surface:** According to its [README](https://github.com/deploymenttheory/go-bindings-win32), it reads Win32Metadata with a native Go reader and generates Win32 functions/types/constants/callbacks/COM. The README reports 324 packages, approximately 17.7k functions, approximately 43.7k COM methods, and approximately 16.5k structs.
- **Architecture and organization:** It separates `bindings/win32/<namespace>`, shared `bindings/runtime/win32`, generator/metadata, and acceptance. Generated files use `windows && (amd64 || arm64)`; 386 is outside its scope. Splitting namespace packages is a useful reference for avoiding huge imports.
- **Types, functions, COM, and WinRT:** It includes structs/unions/enums/handles, inline syscall wrappers, typed COM vtables/methods, callbacks, and ergonomic helpers for strings/bools/errors/slices/handles. WinRT is outside its scope. Raw and ergonomic conversions are not separated into modules/packages as distinctly as this task requires.
- **ABI verification:** [`acceptance/abi_generated_test.go`](https://github.com/deploymenttheory/go-bindings-win32/blob/main/acceptance/abi_generated_test.go) compares metadata-derived expected amd64 layouts for 426 sampled structs with Go `unsafe`. The README also reports a larger count of generated ABI assertions, which must be distinguished from the sample file. This is useful regression coverage, but both sides derive from the same metadata, so it is not an independent MSVC/Clang header oracle. Live acceptance tests verify syscall/COM behavior.
- **Generated output:** Namespace packages, runtime, diagnostics baseline, and acceptance. Generated code is retained in the repository and deterministically regenerated/diffed.

## Boundary Between Reuse and Independent Implementation

The `microsoft/go-winmd` reader is the immediate production dependency reused by this project. Official Win32/WDK/App SDK repositories serve as primary source provenance for retrieving pinned Microsoft metadata/NuGet packages, not as "open-source generated bindings."

Use the following as comparison oracles without copying their generated output:

- `windows-rs`: Win32/COM/WinRT names, signatures, namespace dependencies, parameterized IIDs, and runtime behavior.
- CsWin32: metadata-attribute interpretation, architecture diagnostics, friendly/raw layering, and COM/PInvoke behavior.
- Deployment Theory bindings: Go-specific package splits, syscall/COM/WinRT runtimes, diagnostics ratchets, SDK/WDK deduplication, and NuGet fan-out.
- `x/sys/windows`: safe DLL loading, last-error behavior, UTF-16/handle lifetimes, and behavior of real APIs.

This project independently implements and owns the following:

- source IDs, version/hash/file inventories, and provider interfaces;
- stable symbol IDs based on canonical signatures and provenance-preserving normalized IR;
- status/reason/backend classification for every symbol and an `unclassified = 0` gate;
- capability decisions for Pure Go, assembly, generated C bridges, type-only, and unsupported;
- Clang-AST supplementation for header macros/inline constructs/bit-fields/packed types/flexible arrays;
- independent MSVC/clang-cl ABI oracles and machine-readable mismatches for x86/x64/ARM64;
- separate coverage and regression gates for projection, generation, ABI, and runtime;
- explicit separation of the raw ABI layer and ergonomic layer.

This boundary lets the project draw on mature existing implementations without treating "generated successfully in another language," "compiled in Go," or "matched layouts calculated from the same metadata" alone as complete evidence for the Windows ABI.
